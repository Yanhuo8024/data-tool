## 功能 9 · 信用评分卡

### 是什么？（打比方）
银行每天要面对成千上万的贷款申请。怎么快速判断"这个人借钱会不会还"？

评分卡就是**一张标准化的打分表**，把一个人的各种信息换算成分数，分数越高越安全，低于某个分数线就拒掉。

就像相亲打分表：年龄、收入、学历、有没有房……每项给分，加起来总分够高才考虑。

### 先分清 A / B / C 卡（风控必问，答对显专业）

| 卡 | 全称 | 用在哪 | 预测什么 | 数据来源 |
|---|---|---|---|---|
| **A 卡** | 申请评分卡 | **贷前**审批 | 这个申请人**未来会不会违约** | 申请件资料 + 征信报告 |
| B 卡 | 行为评分卡 | 贷中管理 | 存量客户**未来几个月会不会逾期** | 还款行为、用信额度、消费流水 |
| C 卡 | 催收评分卡 | 贷后催收 | 这笔逾期**能收回多少 / 值不值得催** | 逾期天数、历史还款意愿、触达情况 |

> **本项目实现的正是 A 卡**（`scorecard.py` 的 `build_scorecard()`：输入申请件字段 + 好坏标签，输出可解释评分）。
> B / C 卡与本实现**共用同一套分箱 + WOE + 刻度框架**，差别只在 `target` 定义与特征来源。
> 所以被问"你会做 B/C 卡吗"，正确回答是「**原型已具备，换 target 与特征即可迁移**」，
> 而不是"No"——这正是区分"只调过库"与"懂业务分层"的地方。

### 完整流程（这个流程背下来，非常加分）

```
① 变量分箱  →  ② 算 WOE 和 IV  →  ③ 逻辑回归建模
                                        ↓
⑥ PSI 监控 ← ⑤ KS/AUC/Gini 评估 ← ④ 转成评分刻度
     ↓
⑦ 拒绝推断（校正偏差） → ⑧ 导出 PDF 模型报告
```

| 步骤 | 大白话 |
|---|---|
| **① 分箱** | 把连续变量切成几段。比如年龄切成 18-25、25-35、35-50、50+ |
| **② WOE** | 每一箱的"坏客户占比 ÷ 好客户占比"取对数。本质是把原始变量转成模型好用的标准分 |
| **② IV** | 衡量这个变量预测违约的能力有多强。**太弱的直接扔掉**（省得模型变复杂还没用） |
| **③ 逻辑回归** | 用筛选后的变量建模型，输出"这个人违约的概率" |
| **④ 评分刻度** | 把概率翻译成人能看懂的分数。比如 600 分对应 50:1 的好坏比，每高 20 分（PDO）风险减半 |
| **⑤ KS / AUC / Gini** | 检验模型能不能把坏人和好人分开。**KS = 好坏累计分布差的最大值**；AUC 是整体排序能力；**Gini = 2×AUC−1**。三者越高区分能力越强 |
| **⑥ PSI** | 上线后监控。比较现在的客群和建模时的客群分布差多少，差太多说明模型过期了要重训 |
| **⑦ 拒绝推断** | 校正偏差（见下） |
| **⑧ PDF 报告** | 把整条链路的结果导成一份模型报告 |

### 为什么需要"拒绝推断"？（这是加分点）
银行只知道"放款的客户"后来有没有违约。**被拒掉的那些人，银行永远不知道他会不会还钱。**

只用放款客户建模，样本就已经经过一轮筛选了（能拿到钱的本来就是相对优质的），这样建出来的模型会**低估风险**。拒绝推断就是用统计方法把这个偏差补回来。

### 记住这 3 句就够了（照着念）
> "评分卡解决的是'该不该借钱给这个人'。流程是：先给变量分箱，算 WOE 把变量标准化、用 IV 筛掉没用的变量，然后逻辑回归建模，再把违约概率翻译成业务能看懂的分数。
> 模型好用 KS、AUC 和 Gini 衡量（**Gini = 2×AUC−1**），上线后用 PSI 监控客群漂移。银行侧做的其实是 **A 卡（贷前申请卡）**，B 卡和 C 卡可复用同一套分箱与刻度框架。还有一点很重要——我做了拒绝推断，因为被拒的客户我们不知道他会不会违约，只用放款客户建模是有偏的。"

### ⚠️ 千万别说错的坑
**算 KS 一定要用"违约概率"，不能用"分数"！** 因为分数越高越安全、概率越高越危险，**方向是反的**，用分数算会得到负的 KS。这是你实际踩过的坑，讲出来特别真实。

### 万一被追问
**问：为什么用逻辑回归不用 XGBoost？**
答：信贷是强监管场景，模型必须**可解释**——监管问"为什么拒这个人"，你得一条一条讲清楚。XGBoost 精度可能更高但说不清。业界的做法是两者都跑，XGBoost 当效果上限的参考，真正上线还是用逻辑回归。

**问：IV 多少算好？**
答：低于 0.02 基本没用；0.02~0.1 弱；0.1~0.3 中等；0.3~0.5 强。**超过 0.5 反而要警惕**——可能是用了"贷后才知道"的变量，属于信息泄漏。

**问：PSI 多少要重训？**
答：小于 0.1 稳定；0.1~0.25 要关注；超过 0.25 建议重训。

**问：为什么分箱要单调？**
答：业务逻辑上，收入越高违约率应该越低。如果分箱后 WOE 忽高忽低，说明分箱不合理，模型上线后会不稳定，业务方也没法解释。

## 功能 10 · 机器学习建模

### 是什么？（打比方）
前面那些方法都是"人先想好规则，电脑照着算"。机器学习反过来：**你给电脑一堆例子，它自己找出规律。**

比如你给它 1 万个人的资料和"是否违约"的结果，它自己琢磨出哪几个因素最关键，下次来个新人它就能预测。

### 平台能做什么
| 类型 | 能干的活 | 例子 |
|---|---|---|
| **分类** | 判断属于哪一类 | 会不会违约、明天涨还是跌 |
| **回归** | 预测一个数值 | 预测下个月销量、预测股价 |
| **聚类** | 自动分组 | 把客户自动分成几类人群 |

### 用到的算法（不用背，知道有几类就行）
- 线性类：线性回归、岭回归、Lasso、逻辑回归
- 树类：决策树、随机森林、GBDT、**XGBoost**（这个最出名，效果通常最好）
- 其他：SVM
- 聚类：KMeans、DBSCAN、层次聚类、GMM
- 降维：PCA

**随机森林 vs XGBoost 的区别（常被问）**：
- 随机森林：种很多棵树，每棵树独立投票，最后取平均
- XGBoost：后面的树专门去**纠正前面树的错误**，一轮轮改进，所以通常更准

### 配套的"自动化"功能
| 功能 | 大白话 |
|---|---|
| 自动特征工程 | 自动生成滞后值、滚动平均、增长率、差分这些衍生变量，省得手工造 |
| 交叉验证 | 数据切几份轮流当"考卷"，防止模型只会做"练习册"（过拟合） |
| 网格搜索调参 | 把参数组合全试一遍，自动挑最好的那组 |
| 特征重要性 | 告诉你哪个变量最关键——**业务方最吃这个** |
| 模型版本回滚 | 每次训练存档，新模型不好一键退回上一版 |

### 记住这 3 句就够了
> "机器学习这块我做的是自动化建模工作台。用户传数据选目标，后面的特征工程、多模型对比、交叉验证调参、评估出图全是自动的。
> 评估上分类给混淆矩阵和精确率召回率 F1，回归给 R²，聚类给轮廓系数。我还做了特征重要性输出和模型版本回滚。"

### 万一被追问
**问：怎么防止过拟合？**
答：用交叉验证调参、看学习曲线、控制树的深度和叶节点最小样本数。特征特别多时先按重要性筛一遍。

**问：类别不平衡怎么办？**（比如 1000 个好人只有 20 个坏人）
答：用 `class_weight='balanced'` 让模型更重视少数类；更彻底的是 SMOTE 过采样。评估上不能只看准确率（全都预测"好"也有 98% 准确率），要看 PR 曲线和召回率。

**问：特征重要性和因果是一回事吗？**
答：**不是。** 重要性只说明相关，不代表因果。比如"下雨天雨伞卖得好"和"下雨天交通事故多"高度相关，但你不能说多卖雨伞能减少事故。要谈因果必须用 DID、工具变量这类方法——这也是我为什么把计量模块和机器学习模块分开做的原因。（**答出这句非常有深度**）

**问：模型加载为什么不用 joblib 直接 load？**
答：pickle 反序列化可能执行任意代码。我写了白名单校验，只允许 numpy/pandas/sklearn/xgboost 这些可信的类型，防止加载来路不明的模型文件中招。

## 功能 14 · 反欺诈规则引擎（投消费金融重点）★ 本版新增

### 是什么？（先分清它和评分卡的区别）
贷前要判的是**两件完全不同的事**：

| | 信用风险 | 欺诈风险 |
|---|---|---|
| 问的是 | 他**愿不愿意还** | 他**是不是本人 / 是不是团伙** |
| 主要手段 | **评分卡**（监督模型） | **规则 + 名单 + 关联图谱** |
| 为什么 | 好坏标签多、关系稳定 | **欺诈正例极稀有（常 <1%）、黑产模式迭代快** |

一句话：**评分卡算"能不能还"，反欺诈判"是不是坑"。** 两者是并行的两道闸。

### 做了什么？（三类确定性规则）
`fraud_rules.py`（叶子模块，**不依赖模型**，可复现、可审计）：

| 规则 | 信号 | 级别 |
|---|---|---|
| `device_cluster` 设备聚集 | 同一设备指纹关联的**不同申请人**超阈值 → 中介代办 / 团伙申请 | **HIGH** |
| `velocity_burst` 短时高频 | 同一申请人在滑动窗口内申请次数超阈值 → 撞库 / 批量提交 | **HIGH** |
| `identity_overlap` 信息复用 | 手机号 / 单位 / 联系人被多个申请人共用 → 多头借贷 / 包装资料 | MID |

裁定：任一 HIGH → `reject_review`（转人工复核，**不得自动通过**）；仅 MID → `manual_check`；无命中 → `pass`。

### 为什么用规则而不是模型？（面试必问）
欺诈正例率常低于 1%，监督模型很难学稳；而**黑产模式一两周就变**，模型迭代速度跟不上。
规则引擎的价值在于：**可解释（能告诉审核员为什么拒）、可热更新（改阈值即上线）、可留痕（每笔裁定都有依据）**。
业界实际做法是「**规则打底 + 模型加分 + 人工兜底**」，本项目实现了第一层的完整骨架。

### ⚠️ 工程细节（这些是"真做过"的证据）
- **阈值集中**在一个 `DEFAULT_THRESHOLDS` 字典里，便于审计与按业务调整，不散落在各规则内部；
- **无法解析的申请时间不会拖垮整批**，且会在结论里**诚实标注"n 条未参与本规则"**；
- **单条规则异常不影响其余规则**（反欺诈宁可多报，不可整批漏审）；
- **确定性**：同一批数据跑两次结果完全一致——这是"可审计"的前提。

### 记住这 3 句就够了（照着念）
> "欺诈和信用是两个问题。欺诈样本极少、变化又快，所以主流做法不是训模型，而是规则引擎。
> 我实现了三类：设备聚集（一台设备关联多个申请人）、短时高频（同一人在窗口内申请多次）、
> 信息复用（手机号/单位/联系人被多人共用）。
> 输出是可解释的命中明细，HIGH 级直接转人工复核、不允许自动通过；而且规则是确定性的，跑两次结果一致，可审计。"

### 万一被追问
**问：规则误杀怎么办？**
答：所以分了 HIGH / MID 两级——HIGH 只做"**转人工**"，不直接拒贷；审核员看到的是具体证据（哪台设备、关联了哪几个申请人），可以复核推翻。**规则引擎的目标是"不漏"，而不是"自动决策"。**

**问：阈值怎么定？**
答：集中在一个字典里、支持调用方覆盖。真实落地要先跑一段历史数据看命中率与误报率再定，我做的是**可调框架**。

**问：和评分卡怎么配合？**
答：**并行两道闸**。反欺诈在**最前面**——先把团伙/包装件排掉，这类申请根本不该进入信用评估；
通过后才进评分卡算信用分。顺序反了会把欺诈件当成"信用差的客户"处理，既浪费额度又漏风险。
