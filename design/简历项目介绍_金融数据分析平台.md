## 模块 1 · AI 研究智能体（LangGraph 状态图编排）★ 主打

**做了什么**
用 LangGraph 编排一个能自主调用工具的研究智能体：用户问"帮我看看这家公司值不值得投"，它会自行规划任务、按序调用财务数据 / 比率计算 / 估值 / 检索等工具、观察结果后决定下一步，最终整合为结构化研究报告。支持状态持久化与中断恢复；手上可调 **32 个领域工具**；输出侧做金融指标口径硬约束与"数字—来源"溯源审计；另有对抗式多智能体辩论、跨会话长期记忆与 JSONL 调用轨迹。

**怎么实现**
- `ai_agent.py`：`StateGraph + START/END + MemorySaver`，节点为 `planner → agent ⇄ tools → finalize / force_final`，条件边决定"是否继续调工具 / 是否已达轮次上限强制收尾"。
- 图状态（`state`）**必须整份可 msgpack 序列化**——函数与自定义对象一律不得进图状态，改挂模块级 `_LG_RUNTIME`（以 `runtime_token` 为键，`invoke` 的 `finally` 回收），节点通过 `_lg_cb(cfg)` / `_lg_memory_state(cfg)` 取回。这是 Checkpoint 能落盘的前提。
- 工具注册表 `registry` 统一登记名称 / 描述 / 参数 / 实现；`_TOOL_PARAM_SCHEMA` 为全部 **32/32 个工具**补齐参数 schema（类型、是否必填、说明），供原生 function-calling 与正则解析两条路径共用。
- 四层降级链：**LangGraph 智能体 → 轻量化重试 → 确定性兜底报告 → 诚实提示**。任何一层失败都不会返回空答复。
- `hybrid_retrieval.py`：TF-IDF + BM25 + 语义向量 → RRF(k=60) 融合 → 可选 Cross-Encoder 精排（未启用）。语义向量路由 `semantic_index.py` 提供**零依赖 LSA** 实现（无预训练模型时兜底），可选依赖全部惰性降级。
- `_audit_sources`：从报告抽取数字 token，回到本轮检索原文中找出处，找不到的追加"待核对"。
- 旁路增强（Checkpoint / 轨迹 / 长期记忆）**必须捕获 `(Exception, SystemExit)`**——`SystemExit` 继承 `BaseException`，裸 `except Exception` 挡不住，会把已完成的终稿整个丢弃；但禁止裸 `except BaseException`，要保留 Ctrl+C 传播。

**口语讲法（约 50 秒）**
> "AI 这块是我花精力最多的。目标不是做个聊天机器人，而是做一个能真的干活的助理——用户问'帮我看看这家公司值不值得投'，它得自己想清楚该先拉财务数据、再算比率、再做估值，然后按顺序把这些工具跑完。
> 所以我用 LangGraph 把它做成一张流程图，而不是一条直线的调用链——这样它可以循环、可以判断、可以在某一步卡住的时候停下来让用户确认，而且每一步的状态都存下来，断掉能接着跑。它手上能调 32 个工具，从财务比率、DCF 估值、DID 回归、ARIMA 预测，到自然语言转 SQL 直接查数据库。
> 工程上有个坑我印象很深：LangGraph 的 Checkpoint 要序列化整个状态，所以任何函数、任何自定义对象都不能塞进图状态里，否则序列化就失败。我把这些运行时上下文全部拿出来挂在模块级的注册表里，用 token 取用，跑完在 finally 里回收。
> 第二个重点是防幻觉。金融场景编数据是致命的，所以我做了两件事：一是检索做三路粗召回再按 RRF 融合——**实跑 TF-IDF、BM25 与语义向量三路**，语义路是我用零依赖 LSA 自研的兜底（没装预训练模型也有语义能力）；二是输出层面做溯源审计，报告里每个数字都要能在原文找到出处，找不到就自动标上'待核对'。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| 为什么用 LangGraph 不用 ReAct 循环？ | ReAct 是单条链路的循环，遇到需要分支、并行、人工介入的场景不好表达。LangGraph 用状态图描述，天然支持条件分支、循环和中断恢复，也方便可视化调试。 |
| 图状态为什么要可序列化？ | 因为 Checkpoint 要把它落盘做中断恢复。这是硬约束，不是设计偏好——我最初把回调函数塞进状态就踩了这个坑，后来把运行期上下文全部外置到模块级注册表。 |
| 工具调不动 / 选错工具怎么办？ | 三层兜底：① 规划节点先给出计划约束可选工具；② 原生 function-calling 与正则解析双路径，原生不被采纳时自动降级；③ 轮次上限后强制收尾，走确定性兜底报告而不是空返回。 |
| 四层降级具体是什么？ | LangGraph 智能体 → 轻量化重试（降轮次）→ 确定性兜底报告（基于已有数据生成）→ 诚实提示。目的是任何异常都不能给用户一个空答复。 |
| 多路检索为什么比单路好？ | 关键词检索擅长精确匹配术语（比如"久期"），向量检索擅长语义相近（比如"利率敏感度"≈"久期"）。RRF 按排名融合不依赖分数归一化，比加权求和更稳健；而且因为只看排名，**少一路也只会让召回面变窄、不会让融合整体失效**——这正是我敢把语义路做成"两级实现 + 零依赖兜底"的依据。 |
| Cross-Encoder 为什么不直接用于首轮检索？ | 它要把 query 和每个候选拼一起过模型，计算量随候选数线性增长，全库跑太慢。所以先用廉价方法粗筛 Top-K 再精排，这是工业界标准的召回—排序两段式。 |
| 溯源审计怎么实现的？ | 正则提取报告里的数字 token，回到本轮检索命中的原文片段里找匹配，找不到就追加"待核对"提示，让用户人工复核。 |
| 可选依赖缺失会崩吗？ | 不会。语义模型、Cross-Encoder、XGBoost 都是惰性加载 / 条件注册，未安装时自动降级——语义路落到自研的零依赖 LSA（**仍有语义能力**）、BM25 落到 `_MiniBM25`，不会整个模块崩掉。 |

### 延伸 · 多 Agent 并行协作管线

**做了什么**
单个 Agent 串行跑完"市场面 → 量化面 → 风控面"要 400 秒以上。我把它改成**多 Agent 并行协作管线**：三个领域 Agent（市场分析师 / 量化建模师 / 风控合规官）各自独立跑完整的 ReAct 循环，**毫秒级同时点火**，最后由一个终稿合成节点统一产出研究报告。进一步地，我加了**阶段按需命中**——不是每次都三阶段全跑，而是按用户实际需求只跑命中的阶段。

**怎么实现（四件事）**

1. **并行执行**：`threading.Thread` 三阶段同启 + `queue.Queue` 排空回放事件。总耗时从"三者累加"变成"**最长阶段 + 终稿**"——实测串行 435.1s → 并行 277s，提速 1.57×（`pipeline.stage_start` 三条时间戳落在 5 毫秒内，是并行的直接证据）。阶段间**不传递产出**，跨阶段交叉验证统一交给终稿合成完成（实测终稿会主动纠正某个阶段的主体/数据错位）。
2. **阶段按需命中**（纯规则，零额外 LLM 调用）：四级判定 —— ① 显式全域词（"全面 / 完整 / 全方位 / 尽调" **且** 含"分析 / 研究 / 报告 / 评估 / 方案 / 审查"）→ 三阶段全跑；② 职责关键词命中 → 只跑命中的（可多命中）；③ 挂了数据文件 → 补"量化建模师"；④ 空集保底 → 只跑"市场分析师"。效果：单阶段任务端到端 **48s**（vs 三阶段 211s），每少命中一个阶段就省掉一条完整 ReAct 循环。`PIPELINE_STAGE_ROUTING=0` 可整体回退为三阶段全跑。
3. **并发安全三件套**（并行后必须补，否则互相踩）：① 云端调用节流改为按 `(provider, model)` 分桶加锁，避免三阶段抢同一账户额度时把一个阶段的 429 传染给全部；② 每个阶段派生独立的 `{session}#p{n}` 标识，隔离 LangGraph thread_id / checkpoint / 取消标志；③ 取消信号从基础会话传导到各阶段线程。
4. **阶段级模型钉扎 + 提速**：市场 `glm-5.2` ｜ 量化 `sensenova-6.8-flash-lite` ｜ 风控 `deepseek-v4-flash`（三个互不相同的模型，按能力分工），终稿合成固定首选模型不参与轮换；配合提速三件套（阶段不跑规划、只下发与本阶段相关的工具白名单、精简系统提示，`tools_prompt` 体积下降 50%–78%）。

**为什么用规则而不是让 LLM 判断该跑哪些阶段**
三个理由：**省额度**（LLM 路由本身要一次调用，与"省额度"的目标直接冲突）、**可复现**（规则判定毫秒级、结果确定，同样输入必然同样输出）、**可单测**（写了 17 条回归覆盖路由表与边界）。

**口语讲法（约 45 秒）**
> "最开始我这个 AI 助手是一个 Agent 从头跑到尾，一个复杂请求要 400 多秒。后来我把它拆成三个领域 Agent——一个看市场面、一个做量化测算、一个看合规风险——**并行跑**，最后再合成一份终稿。总耗时就不再是三者相加，而是取决于最慢的那个阶段，实测从 435 秒降到 277 秒。
> 但并行之后我立刻发现两个新问题。一个是三个阶段会抢同一个账户的调用额度，一个阶段被限流会连累其他阶段，所以我把节流从全局改成了按'厂商 + 模型'分桶加锁；另一个是三个阶段互相踩 LangGraph 的状态和取消标志，我给每个阶段派生了独立的线程标识做隔离。
> 更进一步我做了**按需命中**：不是每次都三阶段全跑，而是用纯规则判断用户这句话到底需要哪几个阶段——比如只问'这个策略的合规风险'就只跑风控那一个，端到端只要 48 秒。这个过程我特意没有用大模型来判断，因为多调一次模型就多花钱，而且结果不可复现、没法写单测；规则判定毫秒级、确定性强，我给它写了 17 条回归。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| 并行后为什么还比串行快不了更多？ | 因为总耗时由**最长阶段**决定，而且三个阶段会共享同一个账户的 TPM/RPM 额度——并行会让瞬时额度争抢更激烈。所以并行之外我还做了按需命中来减少阶段数，这才是更大的杠杆。 |
| 阶段之间为什么不传产出？ | 这是有意的：并行执行下阶段互为独立，传产出会引入顺序依赖、把并行退化成串行。交叉验证我统一放在终稿合成——它能看到全部阶段产出，反而比阶段间两两校验更全面。 |
| 为什么阶段要用不同的模型？ | 按能力分工：市场面需要归纳与表达（用通用强模型）、量化测算需要长上下文与稳定输出（用快而稳的模型）、风控需要严格按条目核对（用推理型模型）。同时分散到不同模型也能降低单模型限流的整体影响。 |
| 阶段失败会不会把整份报告带崩？ | 不会。单阶段失败只标记该阶段 `failed`，其余阶段正常产出，终稿按已有信息继续；且失败阶段的降级提示文本**不会**被当作产出喂进终稿（这条我踩过坑，见模块 3）。 |

## 模块 2 · 意图路由与语义护栏 ★ 主打

**做了什么**
AI 助手要同时支撑"知识问答 / 自然语言查数 / 数据操作 / 深度分析 / 故障排查 / 闲聊 / 域外问题"等十类意图，并决定是走知识库抢答、轻量 LLM 简答，还是拉起 Agent 深度分析。我把它做成**规则分层 + 相似度微调 + LLM 精排**的三级路由器，并做了一轮完整的可复现性治理。

**怎么实现（8 层判定 + 4 项治理）**

分层判定（`intent_router.py`）：
`L1 关键词 → L1.4 强信号优先 → L1.45 计算类信号 → L1.48 域外判定 → L1.5 实体感知 → L1.55 指标取值问询 → L1.56 时间限定查数 → L1.6 续接识别 → L2 示例相似度微调 → L3 LLM 精排（仅歧义时触发）`

四项关键治理：

1. **判定确定性**：旧实现用 `set(...)` 迭代建融合分字典，**同分时 top1 取决于 CPython 哈希随机化**，同一句话跨进程可能判出三种意图。改为显式 `_INTENT_PRIORITY` + `_rank_scores()` 有序排序 → 6 个哈希种子下判定逐字节一致。
2. **分层量纲封顶**：旧实现 `kw + 2.0*ex` 允许相似度层直接推翻规则层。改为预算封顶（`_L2_TIE_ADD=1.0` / `_L2_SILENT_ADD=0.5` / `_L2_SIM_FLOOR=0.25`），且 L1 全零时按相似度**占比分配**填空预算；域外与计算类意图明确**排除相似度微调**（曾出现"它现在贵不贵"因字符近似"现在几点了"被判域外）。
3. **边界匹配防污染**：关键词从裸子串改为 `kw_hit()` —— 英文词边界、数字两侧非数字约束、中文语境否决表（`_KW_NEGATIVE`）。修复了 `"hi"` 命中 `which`、`"500"` 命中 `2020/5000` 这类误判。
4. **兜底不再"永不澄清"**：旧实现把闲聊兜底硬编码 `0.8`，而澄清阈值是 `0.55` → **判闲聊的输入永远不会触发澄清**。改为：明确应答语（"好的"）给 `0.9` 不澄清；**L1 全部为零**的零信号输入给 `0.3` 触发澄清；并引入混合意图降权，让"你好，帮我看看这个数据"走业务而非闲聊。

配套工程：`normalize_query` 两遍法（保护标准术语占位符 → 同义词替换 → 还原 → 去相邻重复，修复了 `DIDDID`、`夏普比率比率` 自膨胀）；`_kb_should_yield()` 让同步与流式两条链路共用同一让路判定，消除双轨漂移。

**口语讲法（约 45 秒）**
> "意图识别听着简单，但其实是个挺深的工程问题。我这套是分三级的：第一级是规则，关键词加各种强信号；第二级是示例相似度微调；只有前两级还分不出来的时候，才调 LLM 精排——因为调模型既慢又花钱。
> 做这轮治理的时候我发现几个问题挺有意思。第一个是**不确定性**：我原来用集合去汇总分数，结果同一句话在不同进程里会判出不同意图，原因是 Python 的字典和集合迭代顺序受哈希随机化影响，同分的时候谁排第一是随机的。后来我改成显式定义优先级，才做到跨进程完全一致。
> 第二个是**越权**：相似度那一层原来的加成上限太高，能直接把规则层的判断推翻。我把它改成预算封顶，相似度只能在规则层打平的时候做决胜，不能翻盘。
> 第三个是**兜底把澄清给吃掉了**：闲聊的兜底分我硬编码了 0.8，而澄清阈值是 0.55，所以判成闲聊的输入永远不会反问用户。这个 bug 挺隐蔽的，后来我改成看规则层是不是完全没信号来决定要不要澄清。
> 修完之后严格标注集的准确率从 91.4% 到 100%，边界用例从 70.6% 到全命中，相似度层翻盘从 10.9% 降到 0。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| 为什么不全用 LLM 做意图分类？ | 三个原因：延迟（每次多一次模型往返）、成本（多轮对话放大）、稳定性（同句可能得到不同判定）。规则层能覆盖大部分场景，LLM 只在歧义时精排。 |
| 怎么保证判定可复现？ | 不用集合/字典的迭代序做 tie-break，改成显式优先级数组排序；并且写了回归测试，用 6 个不同的哈希种子跑同一批样例，断言结果逐字节一致。 |
| 相似度层和规则层谁说了算？ | 规则层说了算。相似度只在规则层打平的时候做决胜，且有加成上限；域外和计算类意图干脆不接受相似度微调，避免"它现在贵不贵"被"现在几点了"带跑。 |
| 怎么防关键词子串误命中？ | 做了三层约束：英文要求词边界，数字要求两侧非数字字符，中文维护了一张语境否决表（比如"个数"前面是"这个/那个"就否决，"图"前面是"蓝/草"就否决）。 |
| 澄清机制原来为什么失效？ | 兜底给闲聊打了 0.8 的硬编码分，而澄清阈值是 0.55，所以判闲聊的永远不会触发澄清。改成按"规则层是否完全无信号"来分流：明确应答语不澄清，零信号才澄清。 |
| 三条链路（同步/流式/知识库）会不会判定不一致？ | 会，这是原来真实存在的问题。我把"知识库该不该让路"抽成一个共用函数，三条链路都调它，从 9 条漂移降到 0。 |
| 现在的准确率是多少？ | 严格标注集 100%（58 条全覆盖），边界用例集 34/34 命中，子串污染 0/7，相似度层推翻规则层 0/92。这些都有可复现的评测脚本。 |

## 模块 3 · Agent 全链路加固（稳定性 / 可观测性）★ 差异化

**做了什么**
对"前端 → 路由层 → 编排层 → 意图路由 → Agent 循环 → 32 工具 → LLM 出口 → 旁路"整条链路做了一次系统性体检，用**离线零额度脚本 + 在线探针**取证，定位并修复了 1 个 P0 + 6 个 P1 + 8 个 P2。随后在**多 Agent 并行改造**中又暴露并修掉 2 个 P0（进程级崩溃、限流误判）。其中最有价值的不是修了哪几个 bug，而是**建立了一套"先取证再动手"的排查方法**和一条数据否决的"伪优化"结论。

**怎么实现（挑 7 项主讲）**

1. **P0 调用形态缺陷**：规划节点只用一条 `system` 消息调 LLM，智谱接口必然返回 `400 code 1214 messages 参数非法` → 复杂任务的 Plan-and-Execute **静默降级为"无计划"**。
   > 排查方法值得一说：我没有只看日志，而是写了两条在线探针做对照——仅 system 消息 → 400；system + user → 200。然后全局排查 15 处 LLM 调用点，确认这是唯一病灶。**任何 `chat([...])` 都要求以 user 轮结束。**
2. **缓存陈旧**：工具缓存键只含工具名 + 参数，无任何失效点。上传同名文件覆盖后，`describe / overview / columns / head` 最长 900 秒返回**旧文件的结构**，与真实数据矛盾。改为缓存键混入文件指纹（`mtime_ns:size`）+ 新增定向失效接口，并在上传 / 删除 / 归档 / 回滚四处接线。
3. **会话隔离双缺口**：会话记忆是进程级单例、无会话维度；路由缓存键仅为消息明文。导致切换会话后首句"然后呢"被续接成**上一个会话**的意图且不澄清。改为按 `conversation_id` 分桶 + 缓存键升级为 `会话␟轮数␟末意图␟文本`。
4. **三层超时护栏**：原先全文 0 处 timeout，最坏单请求约 1200 秒，且流式卡死时只无限发心跳（前端永久转圈）；WSGI 仅 8 线程，8 个卡死即全站 AI 不可用。补齐：单工具 90s / 整轮墙钟 600s（超时转强制收尾）/ 流式看门狗 300s。
5. **降级状态不可见**：Agent 返回了 `truncated / degraded / end_status / resumable / trace_id`，但出口用白名单重建字典时**全部丢弃**，前端 0 处消费 → 被轮次上限截断的报告按完整报告展示。改为全字段透传 + 前端降级提示条与执行轨迹入口。
6. **P0 · 第三方 V8 引擎并发创建直接把进程打死**：三阶段并行后，服务进程在运行中**整体消失**，日志只剩一行 `[FATAL:partition_address_space.cc(243)] Check failed: !IsConfigurablePoolInitialized()`，栈顶是 `py_mini_racer`（akshare 依赖的 V8 绑定）。**Python 层无法捕获**——不是异常，是进程直接终止。定位方式是自己写探针做并发梯度复现：并发 1 正常、**并发 3 / 5 均 100% 崩溃**，确定是"多线程同时创建 `MiniRacer()` 会重入初始化 V8 configurable pool"。修法是把包属性 `py_mini_racer.MiniRacer` 替换成**带全局锁的工厂**——akshare 走属性查找，替换即覆盖全部调用点，**无需改第三方代码**，返回的仍是原生实例（类型不变），并留 `DT_MINI_RACER_PATCH=0` 开关可回退。回归测试的并发用例**必须子进程隔离**：若直接写在 pytest 里，补丁一旦回退 FATAL 会带走整个测试会话，连失败信息都看不到。
7. **P0 · 限流下的"假成功"判据**：阶段成功判据原为"产出非空"（`bool(reply)`）。但 Agent 的失败路径会返回 `ok=False` + 一段**非空**的降级提示（如"配额耗尽"133 字）。于是被限流的阶段被判成**成功**——`degraded=false`、`failed_stages=[]`，健康面板完全看不出异常；更严重的是这段提示被当成"阶段产出"喂给终稿，最终报告被写成"因接口限流无法进行分析"的**错误说明书**。修法：判据改为 `bool(reply) and r.get('ok') is not False`（有产出 **且** 未显式报失败），失败阶段的降级文本一律不喂终稿。连带补上 `agent_loop` result 契约缺失的 `end_status` 字段（原缺失导致前端只看到"阶段失败"、看不到原因）。同批次还修掉"终稿只剩 29 字符"——管线终稿合成是**直接 `chat()` 的独立路径**，不在图节点的收尾逻辑里，所以没有继承后者的关思考配置，被推理模型的思考吃满了 token 预算；对推理系模型显式关闭思考并把 `max_tokens` 提到 4800 后，终稿恢复到 4000 字量级。

### 延伸 · 工作流可视化画布（可观测性落地）

**做了什么**
平台本就记录了 JSONL 调用轨迹，但只有原始事件流和两张简易诊断页。我把它升级成一个**画布式的工作流可视化器**：把某一次真实运行回放成一张可交互的流程图——节点拓扑、并行工作组、逐步计时、失败阶段标红、事实核查统计一屏可见；既能"跟着最新一次运行"实时滚动，也能"钉住某一次"定格复现，特别适合演示和排障。

**怎么实现**
- **取数走进程内直读**：可视化适配层直接读轨迹存储，不再经由独立桥接服务（少一次网络往返，也不受端口配置与限流影响）。
- **接口同源**：新增 `/api/assistant/flowviz/{runs,spec,state,raw}` 四个接口，挂在**随 import 同步注册**的核心蓝图上，避开懒注册带来的 404 竞态。
- **iframe 隔离承载**：可视化器是自带主题变量与全局命名的单文件全屏应用，直接用 iframe 隔离，避免与主站 CSS/JS 命名冲突；209KB 的页面在首次点开标签页时才懒加载，不拖慢首屏。
- **语义口径对齐**：顺手修掉移植过来的三处旧口径错误——事实核查的 `ratio` 是**未核验率**（>0.5 报警）而非"核验率"；`force_final`（达轮次上限正常收尾）与 `truncated`（终稿真被截断）必须拆开报，不能混为一个"输出截断"。这两处判断反向，会把健康的报告标成问题、把真问题标成健康。
- **验证**：无头浏览器端到端 13/13（节点渲染、并行分支、失败阶段标红、未核验率文案、主站无 JS 报错全部断言）。

**口语讲法（约 30 秒）**
> "可观测性这块我没有停在'写日志'。平台本来就在记调用轨迹，我把它做成了一个画布可视化——一次真实运行能回放成一张流程图，哪个阶段跟哪个阶段并行、各自跑了多久、谁失败了、事实核查有多少数字没找到出处，一屏就能看见。它还能'钉住某一次运行'定格看，演示和排障都靠它。
> 顺手我还纠了一个很容易骗人的口径问题：事实核查那个比例是'未核验率'，原来的可视化代码按'核验率'来判，方向正好反了——健康的报告被标成问题、真正有问题的反而标成健康。"

**一次用数据否决的"伪优化"**（面试很加分）
原本计划做"单轮多工具并行执行"。分析 340 份调用轨迹后发现：**135 轮里仅 4 轮含 2 个以上工具，绝大多数轮次只有 1 个工具**——并行收益几乎为零，却要引入并发调度与错误聚合的复杂度。结论：明确不做。同类需警惕的还有"扩大缓存"、"增加轮次"、"再加提示词约束"。

**口语讲法（约 55 秒）**
> "这块是我做的最有价值的一件事——我没有急着改代码，先花时间把整条链路摸清楚，写了一套离线诊断脚本，能零成本跑完全链路体检，再配合在线探针做对照验证。
> 最典型的一个 bug：规划节点调模型的时候只传了一条 system 消息，没有 user 轮。这是很多大模型的硬性要求，所以接口直接报参数错误。但因为它有兜底，程序不崩，只是**静默地降级成"没有计划"**——也就是说，最需要规划的复杂任务反而拿不到规划。这种 bug 看日志很容易被忽略。
> 我的排查方法是做对照实验：先单独验证'仅 system 会失败'和'加了 user 轮能成功'，再全局搜所有 15 处模型调用点，确认只有这一处有问题。这样修完能确定是根治，不是碰巧。
> 还有一个是超时。原来整个 agent 模块一行超时都没有，最坏情况一个请求能挂 20 分钟，而且流式接口在卡死的时候只会一直发心跳，前端就一直转圈。后来我补了三层：单工具 90 秒、整轮 600 秒、流式看门狗 300 秒，保证最坏情况下也一定会返回一个带降级标记的结果，而不是无限等。
> 最后有个我觉得挺有意义的结论：我本来打算做工具并行执行，但分析历史轨迹发现 135 轮里只有 4 轮是多个工具，并行几乎没有收益，反而要引入并发复杂度。所以**我用数据把这个优化否掉了**——不是所有能做的优化都值得做。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| 为什么超时线程不 kill？ | Python 限制：线程无法被强杀。我的做法是主流程立即拿到超时错误继续推进，底层 daemon 线程等它自己返回后回收。要真正可中断得上子进程，但那样数据传递成本太高、不值得。 |
| 三层超时各自解决什么？ | 单工具 90s 防单个联网/取数卡死；整轮 600s 是整条请求的墙钟预算，超了转强制收尾保证有输出；流式看门狗 300s 解决"前端永久转圈"，超时主动结束流并推降级事件。 |

## 模块 4 · 多因子模型与策略回测

**做了什么**
从 A 股自选股票池拉日频行情与季度财务数据，按 Fama-French 五因子方法构造五个因子收益率序列（市场 MKT、规模 SMB、价值 HML、盈利 RMW、投资 CMA），做因子统计描述与相关性分析；同时在个股维度提供 CAPM 回归（算 α、β）、双均线交叉与 MACD 两种择时策略回测，输出年化收益、波动率、夏普、Sortino、Calmar、最大回撤、胜率，并叠加基准指数走势对比。

**怎么实现**
- `factor_model.py`：股票池 `fetch_stock_pool`（默认 40 只、剔除 ST、上市满 365 天）→ 日频收益与财务指标 → `_group_breakpoints` 分组 → `build_factor_returns` 构造因子 → `factor_statistics` 统计 → `cumulative_curve_chart` / `correlation_html` 出图。
- 分组口径：市值按 50% 分位切小/大；账面市值比 BM 与 ROE 按 30%/70% 分位切三组；投资因子用总资产同比增速分组；组内日频等权、季度调仓。
- `finance_quant.py`：`capm_analysis`（α、β、无风险利率默认 2%）、`backtest_ma_crossover`（默认 5/20 日均线）、`backtest_macd`（12/26/9）；`_calc_drawdown` 算最大回撤；胜率 = 盈利交易日 / 有仓位交易日。
- `benchmark.py`：`get_index_kline` 拉基准指数，`align_benchmark_to_strategy` 按日期对齐策略收益；`BENCHMARKS` 维护 5 个指数代码映射。

**口语讲法（约 40 秒）**
> "因子这块我做了完整的 Fama-French 五因子。简单说就是想回答一个问题：一只股票的涨跌，到底有多少是大盘带的，有多少是因为它盘子小、或者估值低、或者盈利好。
> 做法是从 A 股选一批股票池，拉日频行情和季度财报，按市值中位数分大盘股小盘股，按账面市值比和 ROE 按 30、70 分位分组，投资因子用总资产增速分组，组内等权、按季度调仓，就能构造出五个因子的收益序列，再看每个因子的表现和它们之间的相关性。
> 另外个股层面还做了 CAPM 回归算 α 和 β，以及双均线和 MACD 两种择时策略回测，输出年化收益、夏普、最大回撤、胜率，并把基准指数画在同一张图上对比。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| 为什么用五因子不用三因子？ | 三因子解释不了"盈利好、扩张保守的公司收益更高"这类现象。五因子加了盈利 RMW 和投资 CMA 两个维度，对 A 股成长/价值风格分化明显的市场解释力更强。 |
| 回测有没有考虑手续费和滑点？ | **诚实答：目前这一版没有建模交易成本，只算了毛收益。** 双均线换手不低，实盘加成本后会明显磨损，这是我下一步要补的。主动承认比被戳穿好，还能顺势讲改进计划。 |
| 因子分组为什么用 30/70 而不是三分位？ | Fama-French 原始论文的做法，30/70 分组能让高低两组差异更显著，避免中间组稀释因子暴露。 |
| 回测结果好不好？怎么避免过拟合？ | 双均线上用的是默认参数，没有刻意调参拟合历史。要真的上线必须做样本外检验和参数敏感性分析——跑一组参数网格，看结果是否稳定在一个平台而不是尖峰。 |
| 数据复权怎么处理的？ | 统一用上市日锚定的后复权价（收盘价 × 复权因子）。不同数据源在股改对价这类事件上可能差一个常数倍，但不影响区间收益率。 |

## 模块 5 · 组合绩效与 Brinson 归因

**做了什么**
把组合相对基准的超额收益拆成三块：资产配置效应（押对了行业/板块）、个股选择效应（板块里选对了股票）、交互效应（两者叠加）。同时提供多基准对比与**基金净值的风险收益评估**——输入一段净值序列，输出年化收益、最大回撤、夏普、Sortino（下行波动版夏普）、Calmar（年化收益 ÷ 最大回撤）五项指标，用于横向比较不同基金的收益质量。

**怎么实现**
`brinson.py`：配置效应 =（组合权重 − 基准权重）× 基准收益；选择效应 = 基准权重 ×（组合收益 − 基准收益）；交互效应 =（组合权重 − 基准权重）×（组合收益 − 基准收益）。三者相加正好等于总超额收益，恒等式成立。
净值指标在 `routes/finance_routes.py`：复用基准指标计算，叠加 `calmar = 年化收益 / |最大回撤|` 与 `sortino = (年化收益 − 无风险利率) / 下行波动率`。

**口语讲法（约 30 秒）**
> "组合这块我做了 Brinson 归因。场景是：基金经理跑赢了沪深 300 五个点，但他自己也不知道这五个点怎么来的。
> 我就把它拆成三部分：配置效应是他超配了某个表现好的行业带来的收益；选股效应是行业权重跟基准一样，但他在行业内挑的股票更好；交互效应是两者叠加。这样一眼能看出这个基金经理是靠押赛道还是靠选个股，这直接决定业绩能不能持续。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| 三效应怎么算的？ | 配置 = (w_p − w_b) × R_b；选股 = w_b × (R_p − R_b)；交互 = (w_p − w_b) × (R_p − R_b)。三者相加正好等于总超额收益，恒等式成立。 |
| Brinson 有什么局限？ | 它是单期静态模型，多期要用 Carino 或 GRAP 做平滑链接，否则各期效应加总对不上累计超额收益。我目前实现的是单期拆解。 |
| 为什么选沪深 300 做基准？ | 视策略风格而定。大盘价值配沪深 300，中小盘配中证 500，成长风格配创业板指。平台把五个基准都接进来了，让用户按风格选。 |
| 夏普、Sortino、Calmar 三个指标为什么要都给？ | 它们惩罚的风险不同。夏普惩罚全部波动，Sortino 只惩罚下行波动（上涨波动不该算风险），Calmar 用最大回撤衡量"最惨一次"的代价。高波动但长期上涨的基金在夏普下吃亏、在 Sortino 下就好看——所以三个一起看才不会误判。 |

## 模块 6 · 财务分析与估值（DCF + 杜邦）

**做了什么**
财务侧做杜邦 ROE 拆解（净利率 × 资产周转率 × 权益乘数）与全套财务比率计算；估值侧做 DCF 自由现金流折现（含 WACC、永续增长率、敏感性分析）与可比公司相对估值（PE/PB/PS/EV-EBITDA 分位数）。

**怎么实现**
`ai_agent.py` 的 `financial_ratios` 工具做杜邦拆解与比率计算，`stock_valuation` 工具做 DCF 与相对估值；`valuation.py`、`company_analysis.py`、`financial_statement.py` 提供底层计算与全景研究模板。

**口语讲法（约 30 秒）**
> "财务这块做了两块。一块是杜邦拆解，把 ROE 拆成净利率、资产周转率、权益乘数三者的乘积——同样 20% 的 ROE，靠高毛利赚的、靠周转快赚的、还是靠加杠杆堆出来的，质量完全不一样，这个拆解能一眼看穿。
> 另一块是估值，做了 DCF 绝对估值和可比公司相对估值。DCF 我做了敏感性分析，因为折现率和永续增长率稍微动一点，估值结果能差好几倍，所以必须给出参数矩阵而不是一个数。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| WACC 怎么算的？ | 股权成本用 CAPM（无风险利率 + β × 市场风险溢价），债务成本用有息负债利率 ×（1 − 税率），按目标资本结构加权。 |
| DCF 的永续增长率怎么定？ | 一般不超过长期 GDP 增速（2%~3%）。我做成了可调参数并输出敏感性矩阵，避免单点估计给出虚假精度。 |
| 相对估值和 DCF 结果打架怎么办？ | 正常现象。DCF 反映内在价值，相对估值反映市场情绪，两者的差就是投资机会或风险提示。我会两边都给，让用户自己判断。 |

## 模块 7 · 计量实证：DID 双重差分

**做了什么**
政策效果评估的完整实证流程：双向固定效应回归估计处理效应，配套平行趋势检验、安慰剂检验、中介效应、异质性分析、子样本稳健性检验与交互分析。

**怎么实现**
`did.py`：`did_regression` 用 linearmodels 做个体 + 时间双向固定效应，核心系数是 treat×post 交互项（post 支持显式列、policy_year 或中位数自动推断）；`parallel_trends` / `placebo_test` / `mediation_analysis` / `heterogeneity_analysis` / `subsample_regression` / `interaction_analysis` 六个检验函数。

**口语讲法（约 45 秒）**
> "计量这块我做的是 DID 双重差分，主要用来做政策评估。比如我自己在研究长期护理保险试点对家庭消费结构的影响，用的就是这套。
> 核心逻辑很简单：找一批受政策影响的地区当处理组，再找一批没受影响的当对照组，比较政策前后两组的变化差了多少，这个'差值的差值'就是政策效果。
> 但光跑出一个系数不够，评审一定会质疑，所以配套做了一整套检验——平行趋势检验验证前提，就是政策前两组走势应该差不多；安慰剂检验是故意把政策时间提前，如果这时候还能'算出'效果，说明原结论是假的；还有中介效应看政策通过什么路径起作用，异质性分析看对哪类人群效果更强，子样本检验看结论稳不稳定。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| DID 的核心假设是什么？ | 平行趋势假设：没有政策时，处理组和对照组结果变量的变化趋势一致。这是识别的命门，所以必须做平行趋势检验。 |
| 为什么用双向固定效应？ | 个体固定效应吸收掉地区不随时间变的差异（比如地理位置），时间固定效应吸收掉所有地区共同面临的时间冲击（比如宏观周期），剩下的才是政策的净效应。 |
| 标准误怎么处理？ | DID 里同一地区不同年份的误差项通常相关，要用聚类标准误（聚到个体层面），否则标准误会被严重低估、显著性虚高。 |
| 安慰剂检验具体怎么做？ | 两种：一是把政策实施时间提前 1~2 年，二是随机虚构处理组，重复跑回归看系数分布。真实效果应该落在分布之外。 |
| 中介效应怎么做的？ | 检验"政策 → 中介变量 → 结果变量"这条路径，看加入中介变量后核心系数是否下降，下降说明存在中介传导。 |

## 模块 8 · 固定收益分析

**做了什么**
债券层面算麦考利久期、修正久期、凸性、DV01、应计利息与全价/净价；组合层面做加权久期与持仓汇总；曲线层面做收益率曲线构建与形态分析（陡峭/平坦/倒挂、关键期限利差）；信用层面做信用利差计算与利率冲击压力测试。

**怎么实现**
`routes/fixedincome_routes.py` 五个端点：`/bond`（单券指标）、`/portfolio`（组合汇总）、`/curve`（曲线分析）、`/spread`（信用利差）、`/stress`（压力测试，按基点冲击 shocks_bp 重估）。支持 JSON 输入与 CSV 批量导入。

**口语讲法（约 30 秒）**
> "固收这块做的是债券的风险计量。核心是久期和凸性——久期通俗讲就是利率变动 1% 时债券价格大概变动百分之几；DV01 更精细，是利率动一个基点这张券的价格变动多少钱。
> 但久期是线性近似，利率变动一大就不准了，所以要加凸性做二阶修正。我还做了收益率曲线形态分析、信用利差，以及压力测试——把整条曲线平行上移或者扭曲多少个基点，看组合会亏多少，这是风控必须看的。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| 麦考利久期和修正久期什么关系？ | 修正久期 = 麦考利久期 / (1 + y/频率)。修正久期才是直接用在价格敏感度上的那个。 |
| 凸性为什么重要？ | 价格—收益率关系是凸的，久期只是切线（一阶近似）。利率变动小时够用，变动大时必须加凸性项，否则会低估价格（无论涨跌，凸性都是正贡献）。 |
| 压力测试怎么设计的？ | 做的是曲线冲击：平行移动若干基点，也可以做陡峭化/平坦化这种非平行冲击，对持仓逐券重估后汇总。 |
| 信用利差怎么算的？ | 同期限企业债收益率减去国债收益率，本质是市场对违约风险的定价补偿，可以做历史分位看当前是贵还是便宜。 |

## 模块 9 · 信用风险评分卡

**做了什么**
信贷风控标准链路：变量分箱 → 计算 WOE 与 IV 筛选变量 → 逻辑回归建模 → 映射到可解释的评分刻度（基准分 + PDO）→ KS/AUC 评估 → PSI 跨期稳定性监控 → 拒绝推断做偏差校正 → 导出 PDF 模型报告。

**怎么实现**
`scorecard.py` 一条龙。分箱结果必须带可复现的 `assign`（edges/groups + woes），训练与打分共用 `woe_assign` 保证口径一致；评估指标必须用**违约概率**而非分数计算——分数越高越安全、概率越高越危险，方向相反，用分数算 KS 会得到负值。

**口语讲法（约 45 秒）**
> "信用风控这块我做了完整的评分卡。业务问题是：一个客户来申请贷款，要不要批、给他打多少分。
> 流程是这样：先把每个变量分箱，比如年龄切成几段，然后算每箱的 WOE——WOE 本质是这箱里坏客户占比跟好客户占比的对比，能把变量转成对模型友好的标准分。IV 衡量这个变量预测违约的能力强不强，太弱的直接筛掉。
> 然后用逻辑回归建模，再把概率映射成大家能看懂的分数，比如 600 分对应 50 倍好坏比，分数每高 20 分风险减半。模型好不好用 KS 和 AUC 衡量。
> 这里有个坑我踩过：算 KS 一定要用违约概率，不能用分数，因为分数越高越安全、概率越高越危险，方向是反的。
> 上线之后还要监控 PSI，看当前客群分布跟建模时比有没有漂移，漂移大了就该重训。另外做了拒绝推断，因为被拒的客户我们不知道他会不会违约，只用放款客户建模是有偏的，得做校正。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| 为什么用逻辑回归不用 XGBoost？ | 信贷是强监管场景，模型必须可解释、可人工审核、能对监管讲清楚每个分数怎么来的。实际做法是两者都跑，用 XGBoost 做效果上限参考，上线仍用逻辑回归。 |
| 什么是 PDO？ | Points to Double Odds，分数每增加 PDO 分好坏比翻一倍，配合基准分确定评分刻度。 |
| 为什么分箱要保证 WOE 单调？ | 业务逻辑上收入越高违约率应该越低。如果分箱后 WOE 忽高忽低，说明分箱不合理或变量本身有问题，会影响模型稳定性和业务解释。 |
| PSI 超过多少要重训？ | 经验阈值：PSI < 0.1 稳定，0.1~0.25 需要关注，> 0.25 建议重训。 |
| IV 值多少算好？ | < 0.02 无预测力，0.02~0.1 弱，0.1~0.3 中等，0.3~0.5 强；> 0.5 要怀疑泄漏了未来信息（比如用了贷后变量）。 |
| 拒绝推断为什么必要？ | 只用已放款客户建模存在样本选择偏差——能拿到贷款的人本来就经过一轮筛选。不做校正会低估风险。 |

## 模块 10 · 机器学习建模

**做了什么**
分类、回归、聚类三类任务，覆盖逻辑回归、岭回归/Lasso、随机森林、梯度提升、XGBoost、SVR/SVC；聚类有 KMeans/DBSCAN/层次聚类/GMM；降维有 PCA。配套自动特征工程（滞后、滚动、增长率、差分、日期、类别交叉、数值交叉）、交叉验证 + GridSearchCV 调参、特征重要性与 R²/precision/recall/F1/混淆矩阵/ROC 评估，以及模型版本管理与回滚。

**怎么实现**
`ml_module.py` 维护模型注册表（XGBoost 为条件注册，导入失败自动降级）；`cross_val_score` + `GridSearchCV` 调参；`feature_engineering.py` 提供 7 类特征变换与 `auto_feature_pipeline` 自动流水线；`routes/ml_routes.py` 提供 train/predict/versions/rollback/compare 完整端点；模型旁挂 `.meta.json` 记录指标与参数；加载走 `secure_safe_load.py` 白名单校验。

**口语讲法（约 40 秒）**
> "机器学习这块做的是一个完整的建模工作台。用户上传数据、选目标变量，后面基本是自动的：先做特征工程，自动生成滞后特征、滚动统计、增长率、差分这些时序特征，还有类别交叉和数值交叉；然后跑多个模型对比，包括逻辑回归、随机森林、GBDT、XGBoost、SVM；参数用交叉验证加网格搜索自动挑。
> 评估方面分类给混淆矩阵、精确率、召回率、F1 和 ROC，回归给 MSE、MAE、R²，聚类给轮廓系数。
> 还有一点是特征重要性输出，业务方很吃这个——他不在乎模型多复杂，他在乎到底哪些因素在影响结果。
> 另外模型有版本管理，每次训练存档指标和参数，新模型效果不好可以一键回滚。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| XGBoost 没装怎么办？ | 惰性降级：导入失败就跳过注册，其他模型照常可用，不会整个模块崩掉。 |
| 类别不平衡怎么处理？ | 逻辑回归和随机森林有 `class_weight='balanced'`；更彻底的做法是 SMOTE 过采样或调整阈值，评估上要看 PR 曲线而不是只看 AUC。 |
| 怎么防止过拟合？ | 交叉验证调参、看学习曲线、控制树深和最小叶样本数；特征多时先做重要性筛选。 |
| 模型加载为什么不用 joblib 直接 load？ | pickle 反序列化可能执行任意代码。我写了 `secure_safe_load.py` 做白名单校验，只允许 numpy/pandas/sklearn/xgboost/lightgbm 等可信前缀的类型，防止加载来路不明的模型文件中招。 |
| 特征重要性和因果什么区别？ | 重要性只说明相关性，不代表因果。要谈因果必须做 DID、工具变量这类识别策略——这也是我把计量模块和 ML 模块分开做设计的原因。 |

## 模块 11 · RAG 混合检索与国家知识库

**做了什么**
知识库检索用 **三路 RRF 融合召回**（TF-IDF + 内置 BM25 + **语义向量**；语义路由 `semantic_index.py` 提供**零依赖 LSA** 实现，不依赖预训练模型）；知识库现有 **142 条**专题条目，含固定收益（收益率、久期/凸性、收益率曲线、信用利差/OAS、债券分类）与基金分析等专题；检索命中后叠加金融指标口径硬约束，避免答非所问。本轮另将知识库召回**接进问答链路**（双源合并召回 + 带引用编号的 LLM 综合作答，引用编号用内容哈希生成、增删条目不错位），终结了此前"只检索、不作答、不落盘"的空壳状态。

**怎么实现**
- `hybrid_retrieval.py`：TF-IDF + BM25 + 语义向量**三路 → RRF(k=60) 融合（实跑）**；语义路为两级实现——装了 `sentence-transformers` 用预训练模型，未装自动落到 `semantic_index.py` 的**零依赖 LSA**（TF-IDF→SVD 降维成稠密向量）；`rank_bm25` 缺失由自研 `_MiniBM25` 顶位；Cross-Encoder 精排为可选依赖（当前未启用）。
- `knowledge_rag.py` / `knowledge_db.py` / `financial_knowledge.py`：条目结构化存储 + 专题分类 + 检索增强。
- `style.css` 之外，知识库数据落 `static/knowledge_data.json`（版本可追溯）。

**口语讲法（约 35 秒）**
> "知识库这块我做了混合检索。单用关键词检索的问题是——用户问'利率敏感度'，我库里写的是'久期'，字面对不上就搜不到；单用向量检索又会丢精确术语的匹配。
> 所以我把三路召回的结果按排名融合（**实跑 TF-IDF + BM25 + 语义向量**；语义路是我自研的零依赖 LSA 兜底——没装预训练模型也照样有语义能力，精排模型则仍未启用）。关键词那两路负责精确匹配术语，语义路负责相近表达，融合之后召回明显更全。
> 另外金融场景对口径特别敏感，所以我在检索之后加了指标口径的硬约束，避免把'年化收益率'和'区间收益率'混着答。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| 多路融合的权重怎么定？ | 没有用加权求和，而是用 RRF。RRF 只看排名不看分数，避免不同检索方法的分数不在一个量纲上需要归一化——这既是它比加权求和更稳健的原因，也是"少一路不会导致融合整体失效"的原因。 |
| RRF 的 k 值取多少？ | k=60，是论文里的常用经验值。它的作用是平滑排名靠前的优势，避免第一名被过度放大。 |
| 检索不到就答不上来怎么办？ | 检索分数低于阈值时直接不注入上下文，宁可让模型说"知识库里没有"，也不要塞一堆不相关内容误导它。 |
| 知识库怎么扩展新专题？ | 条目走结构化存储，按专题分类。目前 142 条，固定收益和基金分析是我专门整理的两个金融专题。 |

## 模块 12 · 数据与工程（投递工程岗时重点讲）

**做了什么**
多源行情适配（akshare / tushare / baostock）与复权口径对齐；DuckDB 列式查询引擎；DataFrame 二级缓存（内存 + 磁盘）与 Gzip 压缩；接口限流；插件与代码执行沙箱；SQL 只读守卫；数据血缘事件日志；模型版本回滚；全局搜索（⌘K）。

**怎么实现**
- **代码执行沙箱**（`sandbox_exec.py`）：子进程隔离 + **Windows Job Object 内存限额**（`CreateJobObjectW` + `SetInformationJobObject` + `AssignProcessToJobObject`，进程内存上限 512MB）+ 执行超时；支持 Python 与 JavaScript 两种运行时。
- **插件静态审计**（`plugin_sandbox.py`）：基于 AST 的静态检查——import 前缀白名单（pandas/numpy/sklearn/matplotlib 等）、危险模块黑名单（os/sys/subprocess/socket/ctypes/importlib）、危险函数黑名单（eval/exec/compile/open/input/`__import__`）、禁止通配导入与 dunder 逃逸。
- **SQL 只读守卫**（`sql_guard.py`）：只允许 SELECT，强制超时与 LIMIT。
- **数据血缘**（`data_lineage.py`）：记录产出文件的上游来源（哪次上传、哪次清洗、哪次归档）。
- **全局搜索**（`static/js/global-search.js` + ⌘K）：跨数据集、指标、任务、标签页的统一检索入口。

**口语讲法（约 40 秒）**
> "工程这块主要解决两个问题：快和安全。
> 快是靠 DuckDB 列式查询加内存/磁盘两级缓存，还有启动时的模块预热。
> 安全是因为这个平台允许用户写代码、查数据库，所以做了三层：代码执行放在子进程沙箱里，用 Windows 的 Job Object 把进程内存卡在 512MB 并加超时；插件上传先用 AST 做静态审计，import 走白名单、eval/open 这类危险函数直接拒绝；SQL 走只读守卫，只允许 SELECT 并且强制超时和 LIMIT。
> 另外做了数据血缘，任何一个产出文件都能追到它上游是哪次上传、哪次清洗来的。"

**高频追问**

| 追问 | 怎么答 |
|---|---|
| 沙箱为什么不用容器？ | 这是一个面向个人/团队的本地化部署平台，用户机器上不一定有 Docker。用子进程 + Job Object 是零依赖方案，能挡住内存爆炸和死循环，挡不住的是内核级逃逸——这个我会在文档里明确说明边界。 |
| AST 静态审计能挡住什么、挡不住什么？ | 能挡住直白的 `eval`、`__import__`、`os.system` 和动态导入；挡不住通过合法白名单库的间接利用链（比如 pandas 读取任意路径文件）。所以它是纵深防御的一层，不是唯一防线。 |
| 二级缓存的一致性怎么保证？ | 内存缓存加 TTL，磁盘缓存按文件指纹（mtime_ns + size）失效；上传/删除/归档/回滚四个入口都做了定向失效处理。 |
| 你为什么不把 SQL 守卫做成语法树级别的完整解析？ | 成本效益考虑。用正则 + 关键字白名单能覆盖绝大多数场景，完整 SQL 解析要引入重型依赖。但我保留了 LIMIT 与超时这两个兜底，防止只读大查询把库拖死。 |

## 三、已知局限（主动说出来反而加分）

面试被问"有什么不足"，别等对方挖，自己先说，并给出改进方案：

| 局限 | 现状 | 改进方案（说出来） |
|---|---|---|
| 回测未建模交易成本 | 只算毛收益，无手续费、滑点、冲击成本 | 加入双边万三计费 + 滑点参数，对换手率做敏感性分析 |

| 意图路由存在已知不可达边界 | 如裸价格类问句（"这瓶酒值多少钱"）会落到查数意图 | 需扩充词表或引入 LLM 精排兜底；已记录在诊断脚本的"已知限制"段，不做无意义调参 |

## 五、术语白话速查（被问"这是什么"时这么答）

| 术语 | 一句话说清 |
|---|---|
| 多因子模型 | 假设股票收益能被几个共同因素解释，算出每只股票在各因素上的暴露度，用来分解收益、控制风险 |
| Fama-French 五因子 | 市场、小盘（SMB）、价值（HML）、盈利（RMW）、投资风格（CMA）——在三因子基础上加了"公司赚不赚钱"和"公司扩不扩张" |
| CAPM α/β | β 是跟着大盘波动的敏感度，α 是剔除大盘影响后多赚的部分，即选股能力 |
| 夏普比率 | 每承担 1 单位波动换来的超额收益，越高越划算 |
| Sortino | 只把下跌波动算作风险（上涨波动不算坏事），比夏普更贴合直觉 |
| Calmar | 年化收益 ÷ 最大回撤，衡量赚的钱相对于最惨那次亏损值不值 |
| 最大回撤 | 从历史最高点跌到最低点的最大幅度 |
| Brinson 归因 | 把超额收益拆成：押对行业（配置）+ 行业内选对股（选股）+ 两者叠加（交互） |
| 回测 | 把交易规则放到历史数据上模拟，看过去赚多少、回撤多大（历史好 ≠ 未来好） |
| DID 双重差分 | 比较"受影响组"和"未受影响组"在政策前后的变化差异，差值即政策效果 |
| 平行趋势检验 | DID 前提：没政策时两组趋势应基本一致 |
| 安慰剂检验 | 故意提前政策时间或换假处理组，若还能算出效果，说明原结论是假的 |
| WOE / IV | IV 衡量变量预测违约的能力（筛变量用），WOE 把分箱转成标准分让逻辑回归更好用 |
| 评分卡 | 把客户信息换算成分数的规则表，可解释、可人工审核，信贷风控标准做法 |
| KS / AUC | 衡量模型能否把坏客户和好客户分开，值越高区分力越强 |
| PSI | 比较当前客群与建模客群分布差异，超阈值说明模型该重训 |
| 拒绝推断 | 被拒客户不知道会不会违约，只用放款客户建模有偏，需统计校正 |
| 久期 / 凸性 / DV01 | 久期 ≈ 利率变 1% 价格变百分之几；DV01 是利率动 1 基点价格变动多少钱；凸性是对久期的二阶修正 |
| 收益率曲线 | 不同期限利率连成的线，看形状判断市场对经济和利率的预期 |
| 信用利差 | 企业债比同期限国债多付的利息，反映市场认为的违约风险 |
| 杜邦拆解 | ROE = 净利率 × 周转率 × 杠杆，看清高回报靠的是赚钱能力、周转效率还是借债 |
| DCF 估值 | 把未来自由现金流折算成今天的价值，核心是现金流预测和折现率（WACC） |
| XGBoost / GBDT / 随机森林 | 随机森林是各树投票取平均；GBDT/XGBoost 是后树纠正前树的错误，通常精度更高 |
| 交叉验证 | 数据切几份轮流当测试集，避免只在一组数据上好看（防过拟合） |
| GridSearchCV | 参数组合全跑一遍、交叉验证打分，自动挑最好那组 |
| 特征重要性 | 模型告诉你哪些输入变量贡献最大，用于解释业务和精简变量 |
| R² / 混淆矩阵 | R² 是回归拟合优度；混淆矩阵是分类的"对错分布表"，能算精确率召回率 |
| LangGraph | 用流程图方式编排 AI 每一步（调哪个工具、何时循环、何时结束），比直线调用链灵活可控 |
| StateGraph / Checkpoint | 状态图描述节点与流转；Checkpoint 把每步状态存下来，中断可续跑，也能回退重来 |
| 条件边（ConditionalEdge） | 状态图里"根据当前状态决定下一步走哪个节点"的分支，是实现循环与强制收尾的关键 |
| msgpack 序列化 | 一种紧凑的二进制序列化格式，LangGraph 用它落盘图状态，所以状态里不能放函数 |
| 意图路由（Intent Router） | 先判断用户这句话想干什么，再决定走知识库、轻量问答还是深度分析 |
| 哈希随机化 | Python 对字符串哈希加了随机种子，导致字典/集合的迭代顺序在不同进程里可能不同——这是"同分判定漂移"的根因 |
| RAG | 先检索资料再让模型基于资料回答，而不是凭记忆瞎编 |
| 混合检索 / RRF | 关键词（BM25、TF-IDF）与语义（向量）各有优势；RRF 按排名融合，不依赖分数归一化 |
| Cross-Encoder 精排 | 粗筛后逐条精细比对相关性，把真正相关的排前面（更准但更慢） |
| 幻觉 | 模型一本正经编造不存在的事实，金融场景尤其致命 |
| 数字—来源溯源 | 报告每个数字都要能在原文找到出处，找不到自动标注"待核对" |
| NL2SQL | 把"查一下去年营收前十的公司"翻译成数据库能执行的 SQL |
| 四层降级 | 智能体 → 轻量化重试 → 确定性兜底报告 → 诚实提示，保证任何异常都不会返回空答复 |
| Windows Job Object | Windows 的内核对象，可对进程组施加内存上限等硬限制，用于代码执行沙箱 |
| AST 静态审计 | 不运行代码，只解析语法树检查 import 与函数调用是否越界——比运行时拦截更早、更安全 |
| 数据血缘 | 记录每个产出文件的上游来源，任何结果都能追溯到原始数据 |
| 多 Agent 并行协作 | 多个各管一摊的 AI 分头干活、同时开工，最后汇总成一份报告——比一个 AI 顺序做完快得多 |
| 阶段按需命中 | 不是每次都把三个 Agent 全叫上，而是先判断你这句话需要哪几面，只需要一面就只叫一个人 |
| 工作流可视化画布 | 把 AI 一次真实的运行过程回放成一张流程图，看得见谁和谁并行、各跑了多久、卡在哪一步 |
| 未核验率 | 报告里的数字有多少在原文中找不到出处（越低越好，超阈值要报警） |
| "假成功" | 代码以为成功了、其实这步已经废掉——比如被限流后返回一段提示文字，会被当成正常产出继续往下用 |
| 进程级崩溃 | 不是程序报错（能被 try 接住），而是整个进程直接被底层引擎终止，日志里只留一行 FATAL，Python 层接不住 |
